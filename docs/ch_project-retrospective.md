# RobotOps Copilot 项目复盘

## 1. 项目目标

RobotOps Copilot 的目标不是让大模型直接控制机器人，而是构建一个只读诊断辅助系统：接收脱敏故障描述、日志和可选图片，按任务需要读取工程知识、模拟遥测或视觉观察，最后输出带来源、引用、风险、终止原因和脱敏工具轨迹的结构化诊断。

项目要解决的核心矛盾是：机器人诊断需要 LLM 的语言理解和多步规划能力，但工程安全又不能把权限、证据和控制边界交给概率模型自行决定。因此最终架构把“模型擅长的事”和“代码必须负责的事”明确分开。

## 3. 最终架构取舍

### 3.1 LLM 只在 Planner 和生成环节参与

Planner 根据任务和已有观察选择下一步工具；Runner 控制循环；Executor 校验工具名称、参数、权限、超时和输出。Runner 与 Executor 不包含 LLM，也不会因为模型要求而绕过注册表。

这种划分避免把“模型说可以调用”错误地等价为“系统允许调用”。模型决定意图，代码决定权限。

### 3.2 安全分类和工具范围在 Planner 之前确定

`AgentRequestSafetyClassifier` 先识别真实控制、急停绕过、带电操作和执行不可信图片命令等高风险意图。`AgentToolPolicy` 再根据用户实际要求计算最小工具范围，并处理“不、别、不要、无需、不需要、禁止”等否定表达。

高风险请求可以在策略允许时完成低风险只读观察，但最终必须进入 `human_review_required`，不能因为图片看起来正常就升级为操作许可。

### 3.3 RAG 引用由 Python 组装

LLM 只选择本次请求已经存在的证据 ID。文件名、页码、章节、Chunk ID、排名和相似度由 Python 根据真实检索结果构造。最终报告再次执行请求级引用白名单校验，避免模型伪造文档来源。

### 3.4 Vision 观察与工程事实分层

图片首先经过 Base64、真实格式、文件大小、边长、像素数和解压缩风险校验。Vision 输出只描述可见文字、指示器、部件状态、不确定项和人工复核需求，并标记 `source="vision_model"`。

知识库事实标记为 `knowledge_base`，模拟遥测标记为 `simulated_memory`。不同来源可以并列，也可以形成冲突。

### 3.5 离线回归与真实模型评测分开

30 条离线场景使用 scripted Planner、Fake Vision 和固定 Fixture，验证的是框架确定性。10 条真实模型抽样调用真实外部 Planner、Vision、Embedding 和知识库，验证的是当前外部链路表现。

离线 `30/30` 与真实严格 `4/10` 不能相加、平均或合并成一个“总体准确率”。人工复核的 6 条通过、2 条部分通过和 2 条失败也不能回写确定性机器评分。

## 4. 关键困难与失败案例

### 4.1 模块边界混淆

早期曾把路由声明误放入 Schema 模块，导致导入阶段出现 `router is not defined`。该问题说明 Schema、Router、Service 和 Dependency 的职责必须保持单向依赖，不能为了快速接通接口把 HTTP 逻辑塞进数据契约文件。

### 4.2 检索高召回不等于最终回答正确

Week 3 的候选检索一度达到 Top-3 完整证据召回率 `0.957`，但最终引用评测仍会因为门控过严、Prompt 输出不稳定或模型没有使用全部必要证据而失败。后续将检索、门控、生成和引用评分拆开统计，避免用候选层指标替代端到端质量。

### 4.3 局部规则容易造成“拆东墙补西墙”

针对单个失败题不断增加关键词规则，可能让当前样例通过，却降低其他场景的工具选择、引用覆盖或任务完成率。项目最终保留通用、可解释的策略：标识符归一化、型号别名、RRF、头部保留重排、证据门控和请求级最小工具范围；撤回了“两次成功检索后隐藏工具”等样例驱动策略。

### 4.4 Planner 输出并不稳定

真实模型曾返回并行工具调用、重复调用、空内容或无效最终 JSON。处理方式不是让 Runner 猜测，而是增加串行化、Schema 校验、重复调用检测、连续失败上限、Planner 超时和稳定降级结果。即便 HTTP 返回 200，执行状态和终止原因仍会明确暴露失败语义。

### 4.5 Vision 能读图，但不等于理解工程语义

真实 Vision 可以正确读取面板文字，也可能把示意图、模糊图片或锁紧环关系判断错。系统因此保留 `partial`、`unusable`、不确定项和 `requires_human_check`，并禁止把视觉观察直接变成设备维修许可。

### 4.6 Docker 故障来自宿主运行状态

最终验收时 Docker Desktop 因 `sailor-ingest.sock.stale` 和 `engine.sock.stale` 残留而无法启动。问题不在项目镜像，而在 Docker Desktop 异常退出后两个运行目录交替残留套接字。通过完整退出 Docker、同时备份两个运行目录并单实例启动恢复，镜像、卷和项目文件均未删除。

## 5. 如何避免为测试样例过拟合

项目采用以下约束：

1. 优先修复通用契约和调用链，不为单个问题硬编码最终答案。
2. 将 Gold 场景、Fixture、真实模型输出和人工判断分开保存。
3. 每次局部修改都运行相关单元测试、30 条离线回归和最终完整 pytest。
4. 同时观察工具选择、任务完成、引用、来源和安全，不只追求单一通过率。
5. 对真实模型失败保留错误码、降级结果和人工结论，不用 Fake 结果冒充真实成功。
6. 当优化造成整体指标波动时，优先回到可解释且全局更平衡的策略。

| 层次 | 结果 | 说明 |
|---|---:|---|

| 安全专项测试 | `34/34` | 已定义安全边界通过 |

## 7. 当前限制

- 系统没有连接真实机器人、RCS、WMS 或生产遥测平台。
- 遥测来自进程内脱敏模拟数据，进程重启后重新创建。
- 所有工具只读；测试草案不会执行。
- 真实模型严格通过率仍为 `0.400`，不能宣称达到生产准确率。
- 没有身份认证、租户隔离、TLS、生产密钥管理、任务队列和集中日志。
- 没有可靠 Token usage，不能给出真实成本。
- 没有工业安全认证，不能替代设备原厂资料和有资质人员。

## 8. 后续方向

1. 为复杂问题增加可审计的子任务分解与“子任务—证据”覆盖矩阵。
2. 在保持引用白名单的前提下，引入独立重排模型或跨编码器并重新建立 Gold 基线。
3. 改进 Planner 最终 JSON 的约束解码、重试和可恢复状态。
4. 为 Vision 增加设备区域检测、图像质量预检和多视角一致性校验。
5. 增加受控对象存储，避免在 JSON 中传输大体积 Base64。
6. 增加认证、权限、审计、任务队列、集中日志和多实例会话存储。
7. 在任何真实设备接入前完成威胁建模、权限评审、仿真验证和工业安全审查。

## 9. 重要的工程认识

这个项目最重要的结果不是“让 Agent 自动做更多事”，而是建立边界：模型负责提出下一步，代码负责决定能不能做；图片负责提供可见观察，知识库负责提供工程依据；证据不足时系统可以拒答，高风险时系统必须转人工。

对机器人场景而言，可追溯、可拒答和可审计比表面上的全自动更重要。
