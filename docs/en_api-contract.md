# RobotOps Copilot MVP API Contract

## 1. Purpose

This document freezes the external API and open data compacts of RobotOps Copilot MVP as the boundaries to which the following modules are common:

- Web console;
- FastAPI Router；
- Agent diagnostic services;
- Agent SSE event publisher;
- Storage of diagnostic sessions;
- Markdown and JSON for certainty export in the Web console;
- End-to-end testing and acceptance scripts.

This document only provides for publicly interchangeable data, does not describe the Planner private reasoning process, and does not allow clients to request an extension of Agent's tool privileges.

## 2. Contract Status

The capabilities in this document fall into two categories:

| Tags | Meaning |
|---|---|
| Achieved | Current Week 7 code already exists and can be called directly or used on the console |
| Not supported for the time being | Not currently MVP's realized capacity |

The current status is as follows:

| Interface | Status |
|---|---|
| `POST /api/v1/agent/diagnose` | Achieved |
| `GET /api/v1/diagnostic-sessions` | Achieved |
| `GET /api/v1/diagnostic-sessions/{session_id}` | Achieved |
| `POST /api/v1/agent/diagnose/stream` | Achieved |
| Web Console JSON/ Markdown Export | Achieved |

## 3. Global rules

### 3.1 Content Type

Normal JSON interface used:

`application/json; charset=utf-8`

SSE interface uses:

`text/event-stream; charset=utf-8`

Markdown Export Usage:

`text/markdown; charset=utf-8`

### 3.2. Request tracking.

Each HTTP request must have `request_id`.

The service end discloses the identification through the `X-Request-ID` response header. Finally, the JSON response, the SSE event and the diagnostic session, `request_id` must be consistent with the response head.

`request_id` for association:

- HTTP response;
- Service redacted logs;
- SSE events;
- Diagnosis reports;
- Diagnosis session.

### 3.3 Session Identification

After the diagnostic session was successfully created, the service returned `session_id` in UID4 format.

`session_id` for subsequent reading and export of diagnostic records. The client cannot specify its own `session_id`.

### 3.4 Untrustworthy input

The following must be considered as untrustworthy:

- `robot_id`；
- `symptom`；
- `log_excerpt`；
- `task_goal`；
- The text in the picture;
- Tool parameters generated by Planner;
- The body of the knowledge base document.

These elements cannot modify the system Prompt, allowlist of tools, security strategy, maximum number of steps, time configuration or evidentiary threshold.

### 3.5 Prohibited public content

No ordinary response, SSE event, session recording or export file shall contain:

- API Key；
- (a) The head of the Authorization request;
- Full picture Base64;
- (a) Local image paths;
- (a) A complete log that is not redacted;
- Planner private thinker chain;
- Complete internal parameters of the tool;
- Full internal return of the tool to the object;
- A directly enforceable robotic control command.

## 4. Agent's diagnostic request

### 4.1 interface

`POST /api/v1/agent/diagnose`

Status: Achieved.

The interface performs a complete diagnosis and returns a JSON response after all processing has been completed.

### 4.2 Request Model

Pydantic model: `AgentDiagnosisRequest`

Achieved location: `app/schemas/agent_api.py`

| Fields | Type | shall fill | Constraints | Meaning |
|---|---|---:|---|---|
| `robot_id` | `str` | Yes. | 1 ~100 characters | The robot number that needs to be diagnosed. |
| `symptom` | `str` | Yes. | 1 ~2000 characters | Faults directly observed by users |
| `log_excerpt` | `str` | Yes. | 1 ~10000 characters | Summary of desensitive logs |
| `task_goal` | `str \| null` | Yes | Maximum of 2000 characters when not available | The goal of this diagnosis is to achieve |
| `images` | `list[VisionImagePayload]` | Yes | Maximum 3 | Picture attached to this request |

The requested model must use `extra="forbid"` to deny the client the submission of undeclared fields, such as:

- `tools`；
- `max_steps`；
- `run_shell`；
- `allow_control`；
- `disable_safety`；
- `retrieval_threshold`。

The client does not have the right to directly specify which tools Agent can use.

### 4.3 Photo Model

Each `VisionImagePayload` contains:

| Fields | Type | Constraints |
|---|---|---|
| `mime_type` | `str` | It can only be `image/jpeg`, `image/png` or `image/webp` |
| `encoding` | `str` | It's currently fixed at `base64`. |
| `image_base64` | `str` | Base64 payload for pictures |
| `analysis_goal` | `str` | 1 ~2000 characters |
| `detail` | `str` | `auto`, `low` or `high` |

Pydantic requests that the model only verify field structures. The decoding of pictures, the matching of real formats and the validity of sizes and pixels continue to be verified by `VisionInputAdapter`.

### 4.4 Example request

```json
{
  "robot_id": "robot-001",
  "symptom": "网络恢复后机器人仍处于暂停状态",
  "log_excerpt": "ERR-NET-4001 heartbeat timeout exceeded 1500 ms",
  "task_goal": "核对故障原因、当前状态和安全恢复条件",
```

## 6. Four types of public diagnostic status

The seventh week must extend `DiagnosisStatus` to:

- `completed`；
- `partial`；
- `abstained`；
- `human_review_required`。

### 6.1 `completed`

The required capacity for the task has been completed, the necessary findings have a credible source and the final report has been structurally verified and quoted as allowlist.

Binding:

- `abstained` must be `false`;
- Evidence must be available to support the final conclusion;
- `missing_information` must be empty;
- Does not mean that on-site operations have been performed.

### 6.2 `partial`

While the system has achieved some credible results, it still lacks the information required to complete all its tasks.

Binding:

- `abstained` must be `false`;
- At least one credible piece of evidence must be present;
- (b) Only part of the conclusion supported by evidence can be returned;
- `missing_information` can't be empty.

### 6.3 `abstained`

The system does not have sufficient evidence to establish a security conclusion or effective tools to return the available results.

Binding:

- `abstained` must be `true`;
- `possible_causes` and `next_checks` must be empty;
- `missing_information` cannot be empty;
- A confirmed source for explaining the conflict of evidence or insufficient evidence could be retained.

### 6.4 `human_review_required`

The request relates to real equipment control, security protection bypasses, high-risk field operations, evidentiary conflicts or must be confirmed by authorized and qualified personnel.

Binding:

- `abstained` must be `false`;
- Read-only, knowledge base or simulated telemetry observations completed can be retained;
- `missing_information` must explain why manual audits are required;
- Directly enforceable equipment control instructions shall not be exported;
- (a) The “need for human review” shall not be downgraded to normal `completed`;
- Even if read-only observation succeeds, the final state can be `human_review_required`.

`human_review_required` is business end, not equal to Agent running failure.

## 8. Quote the contract

The reference in the final diagnosis is used `DiagnosisEvidence`.

The knowledge base query tool is internalized `KnowledgeCitation`. The service level needs to convert it into a final report reference and cannot allow Planner to fill in the file name, page number, similarity or body.

### 8.1 `DiagnosisEvidence`

| Fields | Type | Constraints |
|---|---|---|
| `chunk_id` | `str` | True Knowledge Library Chunk Identification |
| `document_id` | `str` | 64 lowercase SHA-256 |
| `source_file` | `str` | Source filename that does not contain the absolute path of the server |
| `page_or_section` | `str` | Original page number or chapter |
| `rank` | `int` | Only order of reporting level starting with 1 |
| `rrf_score` | `float` | Must be greater than 0 |
| `vector_similarity` | `float \| null` | Range - 1 to 1 |
| `excerpt` | `str` | Original text copied from real Chunk |

`rrf_score` is the integration sequence fraction, not the correct probability of the answer.

`vector_similarity` for `null` indicates that the evidence is only available in keyword candidates, not invalidation.

### 8.2 Quoted Allowlist

The evidence IID allowed for the final report must be the result of a successful implementation of the `search_knowledge` tool in this request.

The following acts must be rejected:

- Planner fiction Chunk ID;
- (a) Use of Chunk, which has been retrieved by other requests;
- Only the name of the document, but not the evidence in the present request;
- The video is a collection of videos that are used in the blog, which is used to describe the video.
- The simulation of telemetry is disguised as documentary evidence.

Pydantic model: `AgentExecutionSummary`

| Fields | Type | Meaning |
|---|---|---|
| `planner_prompt_version` | `str` | Planner Prompt Version |
| `state` | `completed \| aborted` | Runner's normal end? |
| `termination_reason` | `str` | Python Control Decision Reason for Termination |
| `termination_message` | `str` | Discontinuable termination statement |
| `finish_reason` | `str \| null` | Planner, business reasons at the end of normal. |
| `step_count` | `int` | Number of tool steps completed |

| `progress` | `AgentProgress \| null` | Final progress snapshot |
| `missing_information` | `list[str]` | Gaps remaining at the end of implementation |

`step_count` shall be equal to `steps` length, `step_id` shall be incrementally increased from 1.

- `execution.state` indicates that Runner is properly terminated;
- `diagnosis.status` indicates the results of diagnostic operations.

For example, when security strategies routinely identify high-risk requests:

- `execution.state` can be `completed`;
- `finish_reason` is `human_review_required`;
- `diagnosis.status` is `human_review_required`.

It's not running down.

## 11. SSE diagnostic interface

### 11.1 interface

`POST /api/v1/agent/diagnose/stream`

Status: Achieved.

The request is identical to `AgentDiagnosisRequest`.

The response type is `text/event-stream`.

The interface must be replicated at `AgentDiagnosisService` and an independent diagnostic business process cannot be implemented.

### 11.2 SSE Event Structure

Each SSE event consists of:

- SSE `id`: a single-twice increment starting at 1;
- SSE `event`: Types of public events;
- SSE `data`: serialized JSON after Pydantic verification.

The public JSON field for all events is:

| Fields | Type | Meaning |
|---|---|---|
| `schema_version` | `str` | It's currently fixed at `agent-sse-event-v1`. |
| `sequence` | `int` | Consistent with SSE `id` |
| `event_type` | `str` | Event-type sorting field |
| `request_id` | `str` | Current request for trace marking |
| `state` | `str` | Current open life cycle status |
| `message` | `str` | Short, secure, displayed information |

The event model should use the Pydantic joint determination:

`event_type` is discriminator.

The different events can only carry their own permissible fields and cannot be spelled out as contradictory through a large number of optional fields.

### 11.3 Type of event

| `event_type` | Additional Data | Role |
|---|---|---|
| `request_received` | Number of pictures, whether or not they contain the mission target | The request has been verified through the infrastructure |
| `safety_classified` | Policy disposal, cause code | Determine whether to continue, refuse or transfer |
| `tool_scope_decided` | Necessary competencies, authorized toolnames | Open minimum tool range |
| `planning_started` | Next step. | Planner, start deciding on the next step. |
| `tool_started` | Step number, toolname, input summary | The tools are starting to work. |
| `tool_finished` | `AgentToolTraceEvent` | Tool success, empty result, rejection, time overrun or failure |
| `progress_updated` | `AgentProgress` | Finalization of one return to the status machine |
| `diagnosis_finished` | `AgentDiagnosisResponse` | The final results have been validated and sustained |
| `stream_error` | `ErrorDetail`, retry | An open error occurred after the stream started. |

### 11.4 order of events

The normal process meets at least:

```text
request_received
→ safety_classified
→ tool_scope_decided
→ planning_started
→ tool_started
→ tool_finished
→ progress_updated
→ diagnosis_finished
```

The tools can be implemented several times, so that the four intermediate categories of events can be repeated.

Each `tool_started` must have the same `tool_finished` as `step_id` unless the connection is broken or the process has been abnormally terminated.

There can only be one terminal event in a single stream:

- `diagnosis_finished`; or
- `stream_error`。

After sending the terminal event, the service must close the SSE connection.

## 12. SSE Error Processing

When an error occurs before the start of the SSE response, use normal HTTP JSON error response.

The SSE response cannot be changed to the HTTP status code when an error occurs after it has already started, and must send `stream_error` events and close the connection.

When the client voluntarily disconnects:

- The service should stop continuing to send events to the connection;
- The downstream waiting period, which is no longer required, should be cancelled;
- The results of the tools that have been implemented can still be preserved in accordance with the session strategy;
- (b) No forgery of `diagnosis_finished`;
- The console must show that the connection has been broken.

## 13. Unified error response

Pydantic model: `ErrorResponse`

```json
{
  "request_id": "request-demo-001",
  "error": {
    "code": "invalid_request",
    "message": "请求内容不符合接口契约"
  }
}
```

Common HTTP status:

| Status Code | Meaning |
|---:|---|
| `200` | Requests are normally processed at the operational level, including completion, partial results, refusals and manual clearances |
| `404` | A valid session ID does not exist |
| `422` | Request fields, path parameters or query parameters were not verified by Pydantic/FastAPI |
| `502` | LLM, Vision, Embedding or Knowledge Base Upstream returns error or invalid response |
| `503` | Necessary configuration is missing or basic services are not available |
| `504` | Upstream service calls timed out |

Operational `abstained` and `human_review_required` are not HTTP errors and therefore normally return `200`.

## 15. Console diagnostics exported

### 15.1 Achieved position and boundary

The current MVP does not provide an independent server session guide path.

The Web console saves the object in the browser memory of `latestAgentResponse` after receiving `AgentDiagnosisResponse` that has been verified through a service-end contract. When the user clicks the Export button, `exportLatestResponseAsJson()` or `exportLatestResponseAsMarkdown()` of `app/web/app.js` generate a download file.

Support format:

- `json`；
- `markdown`。

### 15.2 JSON Export

JSON exports redacted diagnostic responses already received on the current console and cannot be re-tributed to Planner, LLM, Vision or knowledge base.

Content-Type：

`application/json; charset=utf-8`

### 15.3 Markdown Export

Markdown export is generated by diagnostic response certainty received from the console and verified by the service end.

Content-Type：

`text/markdown; charset=utf-8`

Markdown contains at least:

- Session ID;
- Summary of the request;
- (a) End state;
- Symptoms and sources;
- Vision observation and photo references;
- Simulation of telemetry;
- Possible causes;
- (b) Next check;
- (a) Knowledge base references;
- Tool trace;
- Quantity;
- Missing information;
- Planner, Policy and Prompt version.

Export operations may not regenerate project findings or add to the time of generation.

## 16. Source Layer

The console, SSE and export reports must distinguish between the following sources:

| Source | Credible meaning |
|---|---|
| `user_report` | User-described phenomena do not mean verified |
| `log_excerpt` | User submitted redacted log content |
| `vision_model` | The model's observation of what is visible in the picture is not a knowledge-base fact. |
| `simulated_memory` | Teaching with simulation telemetry, not real production telemetry. |
| `confirmed_knowledge` | Content of the knowledge base confirmed through retrieval and evidence gate control |
| `system_clock` | UTC time for applying the server |

Different sources cannot impersonate each other.

Vision observation can support “what is seen in the picture”, but cannot be independently demonstrated as equipment specifications, failure causes or safety operating requirements.

## 18. End-to-end call chain

General JSON Diagnosis

```text
Web Console (collection of dissensitive text and optional pictures)
→ FastAPI Agent Router (validation of Agent Diagnosis Request)
→ AgentDiagnosisService (Coordination of Request Strategy, Runner and Session Save)
→ AgentToolPolicy and Safety Catalogue (identify business disposal and minimum tool range)
→ AgentRunner (implement controlled planning cycle)
→ ToolExecutor (read-only tool verified and executed)
→ Report builder (execut allowlist references and final data validation)
→ DiagnosticSessionStore (continuous dissension sessions)
→ AgentDiagnosisResponse (return to final JSON)
```

SSE Diagnosis Channel:

```text
Web Console (starting current diagnosis)
→ FastAPI SSE Router (validation request and establishment of SSE connection)
→ AgentEventPublisher (receiving internal progress and generating public events)
→ AgentDiagnosisService (reuse existing diagnostic master process)
→ Agent Runner and Tool Layer (continuous internal state change)
→ AgentEventPublisher (converted to redacted event verified by Pydantic)
→ SSE Router (codified and pushed events)
→ DiagnosticSessionStore (store final redacted session)
→ Diagnosis_finished or sstream_error
```
