## 2. 本周工作在整体 AI 应用架构中的位置

第一周完成的是一个普通的 LLM 应用：

```text
用户输入
→ FastAPI
→ 业务Service
→ LLM
→ 结构化回答
```

这种架构适合摘要、改写和一般性分析，但模型主要依赖训练时学到的知识。对于机器人说明书、故障码、安全标准和内部操作规程，这种方式存在明显问题：

- 模型可能没有见过项目专有资料；
- 模型训练知识可能已经过时；
- 模型可能混用不同型号的参数；
- 模型无法提供可验证的文件和页码；
- 模型可能在证据不足时补全一个听起来合理的答案。

第二周增加了 RAG 证据层：

```text
用户问题
→ Query Embedding
→ 向量检索
→ 取得少量相关Chunk
→ 判断证据是否足够
→ LLM依据证据组织回答
→ Python映射真实引用
```

RAG 没有训练或修改 LLM 本身。它改变的是模型回答前可以访问的信息，以及系统对回答的约束方式。

在整个 AI 应用框架中，本周实现的 RAG 层负责：

1. 将非结构化工程文档转换成可检索知识；
2. 找到和当前问题最相关的证据；
3. 控制哪些问题允许进入生成模型；
4. 为回答提供可追溯来源；
5. 为未来的 RobotOps Copilot 或 Agent 提供受控知识工具。

未来即使加入 Agent，Agent 也不应该直接依赖模型记忆回答工程问题，而应调用本周实现的知识库查询能力。

## 3. 为什么先建立评测集，再开发 RAG API

本周最重要的工程决策之一，是先定义“什么算检索正确”，再开发问答接口。

如果没有 Gold Question，开发者通常只能通过几个临时问题主观判断：

```text
这个结果看起来还不错。
```

但“看起来不错”不能回答以下问题：

- 正确证据是否进入 Top-3？
- 多段证据是否全部召回？
- 无答案问题是否被错误放行？
- 参数调整后是真正变好，还是只改善了某一个例子？
- 回答引用是否真的来自 Gold 预期文档？

因此本周建立了 20 道机器可读取的问题：

```text
16道可回答问题
4道无答案问题
其中包含4道多跳问题
```

每道可回答问题都标注：

- 问题 ID；
- 问题文本；
- 问题类型；
- 参考答案；
- 预期 `source_file`；
- 预期 `page_or_section`。

这样，检索效果就可以通过程序重复计算，而不是依赖主观印象。

## 4. 语料与证据契约的设计

### 4.1 语料选择

本周使用五份公开或脱敏资料：

1. Cognex DataMan 260 公开参考手册；
2. Victron Lithium Smart Battery 公开手册；
3. 工业移动机器人安全标准征求意见稿；
4. 自编、脱敏的仓储机器人故障说明；
5. 根据公开仓储场景编写的测试规程与判定标准。

这些资料覆盖了：

- 传感器；
- 电池和执行器相关参数；
- 安全标准；
- 故障记录；
- 测试规程。

这使评测集既包含英文产品手册，也包含中文故障码、规范条款和跨文档问题，更接近真实的机器人研发知识库。

### 4.2 为什么需要多种数据契约

本项目没有用一个通用字典承载所有阶段，而是为不同处理阶段定义不同的数据契约。

主要转换关系为：

```text
SourceTextSegment
→ DocumentChunk
→ EmbeddedChunk
→ Chroma记录
→ RetrievedChunk
→ Citation
```

#### `SourceTextSegment`

表示 Loader 从原始文件中解析出的一个带位置文本段。

它保存：

- 文本内容；
- 页码或章节；
- 在原始文档中的位置。

它的职责是保留原始文档结构，而不是规定最终 Chunk 大小。

#### `DocumentChunk`

表示经过 Chunker 切分、准备向量化的文本块。

它增加：

- `document_id`；
- `chunk_id`；
- `chunk_index`；
- `content_hash`；
- `source_file`；
- `page_or_section`。

#### `EmbeddedChunk`

表示已经得到 Embedding 向量的 Chunk。

它同时包含：

- Chunk 正文和来源；
- Embedding 浮点向量。

#### `RetrievedChunk`

表示一次查询中从向量库返回的证据。

它增加：

- 检索排名 `rank`；
- 相似度 `similarity`。

#### `Citation`

表示最终返回给 API 调用方的引用。

它包含：

- 文件名；
- 页码或章节；
- Chunk ID；
- 排名；
- 相似度；
- 原文片段。

为各阶段定义不同契约，可以防止下游代码依赖上游尚不存在的字段，也能让测试精确验证每一步的输入和输出。

## 5. 文档解析与切分的工程经验

### 5.1 Loader 和 Chunker 分离

Loader 负责回答：

```text
原始文件里有什么文字？
这些文字来自哪一页或哪一节？
```

Chunker 负责回答：

```text
应该把这些文字切成多大的检索单位？
相邻Chunk需要保留多少重叠？
```

两者分开后：

- 可以更换切分参数而不修改 PDF 解析；
- 可以增加新的文件格式而不修改检索逻辑；
- 可以独立测试解析和切分；
- 原始页码或章节不会因为切分而丢失。

### 5.2 切分参数比较

本周比较了两套参数：

```text
chunk_size=450，overlap=80
chunk_size=800，overlap=120
```

早期 Markdown 预览中，两套参数看起来完全相同。问题不是两种切分真的相同，而是预览函数只展示了相同的开头部分，掩盖了 Chunk 结尾和边界差异。

后续改进预览：

- 增加可见长度；
- 分别标记开头和结尾；
- 避免把不连续的头尾内容显示成一段连续正文。

这说明评测工具本身也需要经过验证。一个不清晰的可视化报告可能让开发者对实际数据产生错误判断。

最终摄取采用：

```text
chunk_size=800
overlap=120
```

固定字符窗口易于理解和复现，但还不能识别表格、列表和语义段落边界。

### 5.3 PDF 英文空格恢复

部分英文 PDF 提取后出现字符或单词粘连，影响：

- 人工阅读；
- 关键词匹配；
- Embedding 语义；
- 最终引用片段质量。

项目加入了启发式英文空格恢复，并使用 Cognex 手册进行了冒烟验证。

修复后建立 `robot_knowledge_v4` 并重新摄取。V4 与 V3 的 Recall 指标相同，但正文可读性和引用质量得到改善。

解析质量除了影响召回率，还影响最终呈现给用户的证据是否可读。

## 6. Embedding 与 Protocol 的设计经验

### 6.1 为什么 Embedding 与 LLM 分开配置

Embedding 模型负责：

```text
文本 → 数值向量
```

生成式 LLM 负责：

```text
问题 + 证据 → 自然语言回答
```

两者职责不同，也可能来自不同服务商，因此配置了独立的：

- API Key；
- Base URL；
- Model；
- 超时和错误处理。

Embedding 模型决定向量空间。同一个 Chroma Collection 中，文档向量和查询向量必须来自同一个 Embedding 模型。

即使两个模型输出相同维度，也不能认为其向量可以相互比较。

### 6.2 `Protocol` 的价值

项目使用 `EmbeddingProvider`、`VectorStore`、`RetrievalStore`、`KnowledgeAnswerProvider` 等 `Protocol` 定义能力契约。

例如业务 Service 只需要知道一个对象具有：

```text
embed_texts()
embed_query()
retrieve()
generate_answer()
```

它不需要依赖具体的 OpenAI SDK 或 ChromaDB 类。

因此真实运行时可以注入：

```text
EmbeddingService
ChromaVectorStore
OpenAIKnowledgeAnswerProvider
```

测试时可以注入：

```text
FakeEmbeddingProvider
FakeRetrievalStore
FakeKnowledgeAnswerProvider
```

这体现了依赖倒置：

```text
业务编排依赖抽象能力
而不是依赖具体外部库
```

`Protocol` 不是负责执行向量化的对象。它只规定“传入的对象必须具备哪些属性和方法”。

### 6.3 Embedding 服务错误

真实运行基线时曾遇到 Embedding API 返回 `404`。

这类错误说明：

- Python 调用链已经成功到达上游；
- 本地批处理和异步调用不一定有问题；
- 更可能是 Base URL、接口路径或服务商兼容方式不正确。

这次排查帮助区分了：

```text
业务逻辑错误
与
外部服务配置错误
```

## 7. 文档去重、延迟写入与 ChromaDB

### 7.1 稳定文档 ID

系统对原文件字节计算 SHA-256：

```text
文件内容
→ SHA-256
→ document_id
```

相同文件内容会得到相同 `document_id`，与文件存放路径无关。

这样可以：

- 检测重复上传；
- 稳定关联文档和 Chunk；
- 按文档删除全部向量；
- 避免重复调用收费的 Embedding 服务。

### 7.2 Chunk ID

Chunk ID 使用：

```text
{document_id}:{chunk_index}
```

例如：

```text
6115fd...32f8:000015
```

它同时表达了：

- Chunk 属于哪个文档；
- Chunk 在该文档中的顺序；
- 同一份文档重新摄取时 ID 仍可保持稳定。

### 7.3 为什么采用延迟写入

摄取流程先完成：

```text
校验
→ 解析
→ 切分
→ 全部Embedding
```

最后才写入 ChromaDB。

这样，如果某一批 Embedding 失败，不会提前留下一个被标记为 `ready`、实际却缺少部分 Chunk 的文档。

这是一种应用层的延迟写入策略，但不等同于数据库事务。当前 ChromaDB 操作仍缺少完整的跨步骤事务和自动回滚。

### 7.4 为什么使用 ChromaDB

ChromaDB 同时保存：

```text
chunk_id
Embedding向量
Chunk正文
来源元数据
```

当前项目不需要单独部署关系数据库，就可以：

- 检索 Top-K；
- 返回原文；
- 按 `document_id` 过滤和删除；
- 列出文档统计；
- 保留可追溯元数据。

它适合当前单机学习项目，但还不具备生产系统需要的权限隔离、高可用、复杂事务和大规模扩展能力。

## 8. 检索评测的迭代过程

检索指标经历了四个主要版本：

| 版本 | Recall@1 | Recall@3 | 无答案错误召回率 | 阶段结论 |
|---|---:|---:|---:|---|
| V1 | 0.300 | 0.600 | 0.000 | 初始持久化检索低于目标 |
| V2 | 0.450 | 0.750 | 0.000 | 有改进，但仍未达到 0.80 |
| V3 | 0.600 | 0.850 | 0.000 | 达到本周目标 |
| V4 | 0.600 | 0.850 | 0.000 | 英文解析改善后保持指标 |

这一过程证明，RAG 不应该在第一次运行后就宣布完成，而应通过失败样例持续检查：

- 正确证据是否存在于语料；
- Loader 是否正确解析；
- `page_or_section` 是否正确；
- Chunk 是否覆盖完整答案；
- Query 和证据的语言表达是否一致；
- 正确证据究竟排在第几名；
- 失败来自检索，还是来自评测匹配。

例如 q013 的第二份预期文档一度排在第五名。通过 Top-10 报告才能看到它不是完全没有被检索到，而是没有进入 Top-3。

最终 q013 在 Top-3 中召回了两份预期证据。

## 9. 当前三个主要检索失败案例

V4 仍有 q007、q008、q009 三道可回答问题未在 Top-3 命中预期证据。

### 9.1 q007：Cognex 线缆远离高压线路

正确证据位于：

```text
ID_reader_COGNEX_Reference_Manual_DM260.pdf
page: 56
section: Precautions
```

实际 Top-3 返回了同一手册中的其他页面。

这说明向量检索识别了产品主题，却没有准确定位到具体的安全注意事项。

可能的改进：

- 中英文 Query Rewrite；
- 为标题和章节名增加检索权重；
- 关键词与向量混合检索；
- 使用 Reranker 对候选 Chunk 二次排序。

### 9.2 q008：Victron 充放电温度范围

正确证据位于手册第 4 页，但检索结果更倾向于第 22 页的电池设置内容。

两处都包含“温度”和“充电”等语义，导致向量检索返回了主题相近但不能完整回答问题的 Chunk。

这说明：

```text
语义相关
不等于
证据完整
```

可能的改进：

- 将数字范围和单位纳入关键词检索；
- 对问题中的 “charge and discharge” 做查询扩展；
- 使用 Reranker 判断哪个 Chunk 能完整覆盖两个温度范围。

### 9.3 q009：ERR-SAF-1002 安全排查步骤

正确证据位于故障说明，但实际结果更偏向急停测试规程和通用安全标准。

对于 `ERR-SAF-1002` 这种精确标识符，纯向量检索可能不如关键词检索可靠。

可能的改进：

- 对故障码进行精确匹配；
- 识别问题中的结构化标识符；
- 使用 BM25 与向量检索融合；
- 对故障码命中的 Chunk 提升排名。

这三个失败案例共同说明，下一步最值得投入的不是继续修改 Prompt，而是增加混合检索和 Reranker。

## 10. 相似度门控与拒答策略

在线问答使用：

```text
Top-1相似度 < 0.60
→ 直接拒答
→ citations=[]
→ abstained=true
→ 不调用LLM
```

这样设计的好处是：

- 防止无证据时让模型自由补全；
- 减少 LLM 调用费用；
- 降低无答案问题的延迟；
- 拒答结果稳定且可以测试。

初始使用较高阈值时，16 道可回答题中只有 1 道被放行。

将在线阈值校准到 `0.60` 后：

```text
可回答题放行数：1 → 7
无答案正确拒答：仍为4/4
```

阈值不是越低越好。继续降低阈值虽然可能放行更多可回答问题，但也会逐渐进入无答案题的相似度分布，增加错误回答风险。

当前阈值是：

```text
基于当前语料
+ 当前Embedding模型
+ 当前Gold Question
```

得到的工程折中，不是可以复用于所有项目的通用常数。

## 11. 为什么引用必须由代码组装

模型收到的每条证据会被分配一个临时编号：

```text
E1
E2
E3
```

模型只允许返回：

```json
{
  "answer": "回答正文",
  "used_evidence_ids": ["E1", "E2"]
}
```

Python 再执行：

```text
E1
→ 当前查询真实rank=1的RetrievedChunk
→ source_file
→ page_or_section
→ chunk_id
→ similarity
→ excerpt
```

这样划分职责：

```text
模型决定回答使用了哪些已提供证据
Python决定这些证据的真实身份
```

如果模型返回不存在的 `E99`，系统会拒绝该输出，而不是生成一个伪造引用。

这比要求模型直接输出文件名和页码可靠，因为文件名、页码和 Chunk ID 都来自程序已经验证过的检索结果。

## 12. 引用评测与 Prompt 修复

### 12.1 第一轮引用评测

较高阈值下的第一轮结果：

```text
实际回答可回答问题：1/16
引用正确率：1.000
引用覆盖率：0.050
无答案正确拒答率：1.000
```

系统非常谨慎，但过度拒答。

### 12.2 阈值调整到 0.60

调整后：

```text
实际回答可回答问题：7/16
引用正确率：0.889
引用覆盖率：0.400
完整证据回答率：0.375
无答案正确拒答率：1.000
```

引用正确率下降并不是检索突然恶化，而是某个回答返回了重复或非必要引用。

### 12.3 最小充分证据规则

Prompt 随后增加：

```text
used_evidence_ids必须是完整支持答案所需的最小充分证据集合。
如果一条证据已经完整支持答案，不得再选择只提供重复背景的证据。
```

修复后：

```text
引用正确率：0.889 → 1.000
完整证据回答率：0.375 → 0.438
```

这说明 Prompt 优化必须针对已经观察到的具体失败行为，而不是无目的地堆叠规则。

## 13. 状态限定词与安全约束

### 13.1 “征求意见稿”遗漏

测试发现，模型可能根据正确证据回答适用范围，却遗漏文件的“征求意见稿”状态。

这在工程上不是措辞小问题。省略状态限定可能让用户把尚未正式发布的文件理解为已经生效的正式标准。

因此 Prompt 增加了状态限定词规则，要求保留：

- 征求意见稿；
- 草案；
- 建议；
- 可能；
- 尚未确认。

同时增加自动化测试，确保 System Prompt 明确要求 `answer` 保留这些限定。

### 13.2 q014 安全禁令遗漏

RAG 与裸 LLM 对照实验中，RAG 初始回答虽然使用了正确的两条证据，却遗漏了：

```text
不允许为了测试而真实堵转电机
```

这说明：

```text
引用正确
不一定代表回答完整保留了安全条件
```

Prompt 随后增加安全约束规则，要求保留与问题直接相关的：

- 禁止；
- 不得；
- 不允许；
- 必须；
- 仅可；
- 操作前置条件；
- 数值阈值。

V2 回答明确包含：

```text
不允许为了测试而真实堵转电机。
```

这次修复说明，对于机器人安全场景，模型不能只保留“做什么”，还必须保留：

```text
什么不能做
什么条件下才能做
什么阈值不能超过
```

## 14. RAG 与裸 LLM 对照实验的结论

对照实验使用相同生成模型和相同问题，但输入不同：

### RAG 组

```text
问题
+ 检索证据
+ 引用约束
```

### 裸 LLM 组

```text
只有问题
+ 谨慎回答规则
```

q014 中：

- RAG 找到了两条项目专有证据；
- 回答可以定位到真实文件和章节；
- Prompt 修复后保留了不得真实堵转的安全禁令；
- 裸 LLM 给出了当前知识库没有支持的通用温度和恢复条件；
- 裸 LLM 还提出了与测试规程冲突的真实堵转建议。

q020 中：

- RAG 在相似度门控阶段直接拒答；
- 没有调用生成式 LLM；
- 返回空引用；
- 裸 LLM 虽然也谨慎拒答，但仍然产生了一次模型调用。

该实验说明 RAG 的主要价值不是保证模型永远回答，而是：

- 为回答提供项目证据；
- 限制知识范围；
- 提供可追溯来源；
- 在证据不足时确定性拒答；
- 避免不必要的模型调用。

单次对照实验会受到模型随机性和网络延迟影响，因此只能作为案例分析，不能替代批量评测。

## 15. API 分层与一次循环导入问题

知识库接口继续沿用：

```text
Router
→ Schema
→ Service
→ 外部Provider或Store
```

各层职责：

### Router

负责：

- HTTP 路径；
- 请求参数；
- 状态码；
- FastAPI 依赖注入；
- 将请求交给 Service。

### Schema

负责：

- 请求和响应的数据结构；
- Pydantic 校验；
- OpenAPI Schema；
- 阻止非法数据进入业务层。

### Service

负责：

- 文档摄取编排；
- 查询向量化；
- Top-K 检索；
- 相似度门控；
- LLM 调用；
- Citation 映射。

开发过程中曾将 Router 代码错误放入 Schema 文件，导致：

```text
dependencies
→ document_catalog
→ schemas.knowledge
→ dependencies
```

形成循环导入，并出现：

```text
partially initialized module
```

之后又因 Schema 文件中存在 `@router.post(...)` 而出现：

```text
NameError: name 'router' is not defined
```

这次问题说明，分层不仅是为了目录整齐，也决定了模块依赖方向。

正确依赖方向应保持：

```text
Router可以依赖Schema和Service
Service可以依赖Schema或领域契约
Schema不应反向导入Router或Dependencies
```

## 16. PowerShell 与 HTTP 调试经验

本周遇到了两类终端问题。

### 16.1 JSON 引号问题

在 PowerShell 中使用 `curl.exe` 时，JSON 字符串经过 PowerShell 和 curl 两层解析，曾导致服务端收到无效 JSON，返回：

```text
422 Unprocessable Entity
JSON decode error
```

后续使用：

```text
PowerShell对象
→ ConvertTo-Json
→ UTF-8字节
→ Invoke-WebRequest
```

减少了手工转义问题。

### 16.2 UTF-8 响应乱码

服务端实际返回的是正确 UTF-8 JSON，但旧版 Windows PowerShell 的 `Invoke-WebRequest` 对响应正文进行了错误解码，导致中文显示为乱码。

这不是 FastAPI 或 LLM 生成乱码，而是客户端解码方式有问题。

解决方案是：

```text
RawContentStream取得原始字节
→ Encoding.UTF8.GetString()
→ ConvertFrom-Json
```

这次问题帮助区分了三层编码：

- 请求发送编码；
- HTTP 响应字节；
- 终端显示和客户端解码。

## 17. 自动化测试策略

最终全量测试结果：

```text
测试节点数：244
通过：244
失败：0
```

自动化测试不访问：

- 真实 LLM；
- 真实 Embedding；
- 外部网络；
- 正式 Chroma Collection；
- 真实 API Key。

主要测试替身：

### Fake

Fake 是一个可控的简化实现。

例如 Fake Embedding 可以根据输入返回固定向量，用于验证：

- 输入顺序；
- 批处理；
- 缓存；
- Query Embedding；
- 文档摄取。

### Mock

Mock 用于记录和控制对象交互，例如验证：

- 某个方法调用了几次；
- 调用参数是什么；
- 是否执行了 `await`；
- 上游超时时是否转换成业务异常。

### 临时资源

`tmp_path` 和临时 Chroma Collection 用于避免测试污染正式数据。

### 依赖覆盖

FastAPI 的 `dependency_overrides` 用于把真实 Service 替换成 Fake Service，从而只验证：

```text
HTTP请求
→ Router
→ Schema
→ Service契约
→ HTTP响应
```

这种设计使测试结果可重复、速度稳定，也避免测试产生 API 费用。

## 18. 本周最重要的认识

### 18.1 RAG 不是一次 LLM 调用

可靠的 RAG 实际由多个子系统共同构成：

```text
语料治理
+ 文档解析
+ Chunk设计
+ Embedding
+ 向量存储
+ 检索
+ 阈值门控
+ Prompt
+ 输出校验
+ 引用映射
+ 评测
```

其中任何一步出错，最终答案都可能不可靠。

### 18.2 检索、引用和回答必须分别评测

三层质量不能混为一个指标：

#### 检索质量

正确证据是否进入 Top-K。

#### 引用质量

返回的引用是否正确、是否覆盖所需证据。

#### 回答质量

回答是否完整保留证据中的事实、限定和安全规则。

本周 q014 就说明了：

```text
检索正确
+ 引用正确
≠
回答一定完整
```

### 18.3 Prompt 不能修复缺失证据

如果正确证据没有进入 Top-K，Prompt 无法凭空恢复它。

因此优化顺序应是：

```text
先检查语料
→ 再检查解析
→ 再检查切分
→ 再优化检索
→ 最后调整Prompt
```

### 18.4 拒答也是正确结果

对于知识库无答案问题，系统最可靠的行为不是生成一个听起来合理的答案，而是：

```text
知识库没有足够证据回答该问题。
```

在工程问答和安全场景中，可靠拒答通常比不受约束的回答更有价值。

### 18.5 有引用不等于可以自动执行

即使回答带有正确引用，也不能直接驱动：

- 急停复位；
- 电机堵转；
- 带电插拔；
- 参数写入；
- 固件升级；
- 机器人运动。

当前系统是知识辅助层，不是安全控制器。

## 19. 当前技术债与限制

### 文档处理

- 没有 OCR；
- 扫描版 PDF 无法可靠提取；
- 复杂表格和多栏排版支持有限；
- 英文空格恢复是启发式规则；
- 固定字符窗口不能识别完整语义结构。

### 检索

- 只有向量检索；
- 没有 BM25 或关键词检索；
- 没有 Query Rewrite；
- 没有 Reranker；
- 故障码和精确型号的权重不足；
- 只根据 Top-1 相似度决定是否放行。

### 生成与评测

- Prompt 仍然属于软约束；
- 当前主要评测引用，不是完整的回答语义评分；
- 没有自动检测全部安全限定词；
- 单次 LLM 实验会受随机性影响。

### 数据与服务

- ChromaDB 是本地单机存储；
- 没有完整事务和回滚；
- 文档摄取是同步请求；
- 没有后台任务队列；
- 没有文档版本管理；
- 没有认证、授权和租户隔离；
- 没有速率限制和审计系统。

### 产品范围

按照本周任务边界，当前没有实现：

- 正式前端；
- Agent；
- 多用户系统；
- 生产部署；
- 实时遥测接入；
- 知识库查询 SSE。

这些不是本周遗漏，而是有意控制范围。先保证证据层正确，再向更复杂的 Agent 和工具调用扩展。

## 20. 本周总结

第二周完成的不只是一个“可以上传文档并聊天”的 Demo，而是一套具备以下工程特征的 RAG 基础设施：

- 输入语料有来源和脱敏说明；
- 文档、Chunk 和引用可以追溯；
- Embedding 和 LLM 职责分离；
- 向量数据可以持久化；
- 重复文档可以拒绝；
- 无证据时由代码确定性拒答；
- 引用不能由模型伪造；
- 检索和引用都有量化指标；
- 测试不依赖网络和真实密钥；
- 已知失败案例被明确记录；
- 架构限制和后续方向清晰。

最重要的工程认识是：

```text
可靠的AI应用不是只关注模型能否生成答案，
而是要控制它依据什么回答、
在什么情况下拒答、
如何证明来源，
以及如何通过评测发现系统仍然不知道什么。
```
