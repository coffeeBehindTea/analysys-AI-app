# Week 3 工程复盘：结构化诊断与RAG可靠性闭环

## 1. 本周目标与结果

Week 2 已经完成文档摄取、向量存储、知识库问答和引用，但线上评测只回答了16道可回答题中的7道。Week 3 的目标不是继续堆叠接口，而是建立一条可以定位“库里有却搜不到、搜到却不放行、放行却没有正确引用”的可靠性闭环，并将证据转换成机器人研发可以审计的结构化诊断报告。

最终结果：

- Gold从20题扩展到28题，其中23题可回答、5题无答案；
- 候选Top-3完整证据召回从纯向量的 `15/23=0.652` 提升到 `22/23=0.957`；
- 可回答问题响应率达到 `20/23=0.870`；
- 完整证据回答率达到 `17/23=0.739`；
- 引用正确率达到 `25/26=0.962`；
- 五道无答案题全部正确拒答；
- 新增结构化诊断API及完整降级路径；
- 完成798项离线自动化测试，全部通过。

## 2. AI应用框架中的位置

完整AI应用不只是“调用一次LLM”，而是由多个可信度不同的层组成：

```text
外部输入
→ HTTP与Pydantic输入边界
→ 确定性查询归一化
→ 检索与候选排序
→ 证据门控
→ LLM生成
→ 结构化Schema校验
→ 证据白名单映射
→ 降级与可观测性
→ 对外响应
→ 离线与在线评测
```

Week 3 主要补齐了中间的“检索可靠性、门控、结构化输出、引用绑定和评测闭环”。这些层存在的原因是LLM擅长语言组织，但不适合承担标识符归一化、权限过滤、引用身份、风险强制规则和稳定降级等必须确定执行的职责。

## 3. 从纯向量到混合检索

### 3.1 纯向量的不足

纯向量检索能够处理语义相近的问题，但对以下输入不稳定：

- `ERR-NET-4001`、`ERR_NET_4001`、`err net 4001`；
- `DM260` 与 `DataMan 260`；
- `-10°C`、`1500 ms` 等数值和单位；
- 中英文手册中的术语对应；
- 需要同时找到两份文档的流程问题。

这些内容包含大量符号级和词面级信息，不能只依赖向量的整体语义相似度。

### 3.2 关键词检索为什么不能单独解决

第一次加入关键词检索和RRF后，Top-3完整证据召回仍为 `15/23`，没有高于纯向量。关键词路径确实救回了错误码问题，但也因为型号别名和中英文表达不统一而挤掉部分向量候选。

这个结果说明“多一条检索路径”不等于“指标必然提高”。两条路径必须先共享稳定的查询表示，并且最终候选窗口需要处理路径竞争。

### 3.3 确定性查询改写的职责

`deterministic-v2` 不调用LLM，而是使用可测试规则完成：

- 错误码分隔符统一；
- 型号别名扩展；
- 数字和单位归一化；
- 特定中英文术语扩展。

这样设计是因为错误码和型号属于确定性标识符。让LLM猜测标识符会增加延迟、成本和不可复现性，还可能把不存在的型号写入查询。

查询改写把完整证据召回提升到 `19/23=0.826`。

### 3.4 头部保留重排的职责

RRF已经将不同量纲的排名转换成统一贡献，但最终Top-3仍可能被某一路的相似候选占满。`head-preserving-v1` 保留RRF Top-1、向量Top-1和关键词Top-2中的互补候选，再按原RRF顺序补齐。

它不是学习型语义重排，也不重新判断正文质量。它解决的是有限候选窗口中的“路径代表性”问题，并保持完全确定、可解释和可测试。

最终完整证据召回达到 `22/23=0.957`。

## 4. 为什么门控不能只看Top-1相似度

Week 2 的单阈值门控容易产生两类问题：

1. 错误码完全匹配，但向量相似度略低，导致可回答题被拒绝；
2. 无答案问题与语料主题相近，Top-1相似度不低，可能被错误放行。

Week 3 的 `hybrid-evidence-gate-v1` 同时检查：

- 精确错误码支持；
- 型号与主题词联合支持；
- 向量和关键词双路径支持；
- 不同问题类型对应的校准阈值。

结果是22/23道可回答题被放行，五道无答案题全部拒绝。门控的目标不是把召回率最大化，而是在进入LLM之前控制“是否有足够依据值得生成”。

## 5. 结构化诊断为什么需要两层Schema

诊断输出使用两层不同的Pydantic契约。

### 5.1 内部 `DiagnosisLLMDraft`

LLM只返回：

- 原因和检查项的文字；
- `E1`、`E2`临时证据编号；
- 风险、缺失信息和拒答状态。

### 5.2 对外 `DiagnosisReport`

Python负责加入：

- Request ID；
- Prompt和门控版本；
- 真实Chunk ID、文件名和位置；
- RRF分数和向量相似度；
- 用户症状来源。

这种分层阻止LLM自行填写文件名、页码、Chunk ID或内部版本。即使模型返回格式正确的 `E999`，只要它不在本次候选白名单中，Builder就会拒绝。

## 6. 降级不是异常处理的附属功能

本周把降级设计成正式业务路径：

- 门控拒绝：不调用LLM，返回稳定拒答；
- LLM主动拒答：保留证据，清空原因和操作；
- 非法JSON、字段缺失、未知引用：转换成结构校验失败报告；
- LLM超时或上游错误：返回固定公开说明；
- 程序Bug：不伪装成正常拒答，继续暴露给错误处理系统。

这一区分非常重要。业务上的“证据不足”应是可预期结果；代码返回错误类型或违反Protocol则是开发缺陷，不能被吞掉。

## 7. Prompt对照实验的结论

基础诊断Prompt在真实案例中返回了状态矛盾的JSON，结构成功率为0。证据优先Prompt明确规定状态关系、引用编号、风险边界和缺失信息后，结构成功率和引用白名单通过率均达到1/1。

但该实验只有一个案例，因此它证明的是：

- 调用链能够执行；
- 结构化规则确实改变了失败模式；
- Pydantic能够拦截非法草稿。

它不能证明Prompt在所有问题上都优于其他版本。

## 8. Prompt过拟合带来的教训

为了修复个别引用评测题，曾经逐步加入：

- 强制先压缩成最少事实；
- 单条证据能够回答时强制只选一条；
- 否定结论特判；
- 严格等号边界特判。

这些规则会形成精确率和覆盖率之间的拉扯：修好一道题的多余引用，可能让另一道多跳题漏掉第二份必要证据；减少拒答，也可能让模型把证据不足解释成有依据的否定结论。

最终回退到通用Prompt，只保留：

- 只根据证据；
- 状态和安全限定词；
- 证据充分与拒答结构；
- 引用白名单；
- 最小充分证据集合。

回退后全部验收指标仍通过，因此停止继续对单题增加全局Prompt规则。

## 9. 评测体系带来的工程认识

### 9.1 候选召回不等于回答正确

候选完整证据召回为 `0.957`，最终完整证据回答率为 `0.739`。两者之间的差距来自：

- 门控拒绝；
- LLM二次拒答；
- LLM少选必要证据；
- LLM多选Gold之外的相关证据。

因此排查顺序必须是：

```text
先看正确证据是否进入候选
→ 再看门控是否放行
→ 再看LLM是否回答
→ 再看引用是否完整且没有多余项
```

### 9.2 Gold本身也是数据契约

`q021` 最初只标注故障说明，后来发现问题还要求安全复位条件，因此修正为两份跨文档证据。修正后早期报告的分母从30变成31，不能直接与新报告并排比较。

最终报告使用保存的候选排名按当前Gold重新评分，保证策略比较采用同一口径。这说明评测数据变更也必须版本化并记录影响。

### 9.3 “完整证据”是严格机械指标

`q013` 和 `q026` 的单个测试规程Chunk已经包含大部分甚至全部回答事实，但Gold要求两份文档，因此仍被标记为不完整。`q024` 的第二份手册页面相关且支持BMS阈值，但不在Gold白名单中，因此计为多余引用。

机械指标适合回归和比较，但不能完全替代人工语义复核。

## 10. 最有效的工程实践

本周最有效的做法包括：

1. 先建立失败台账，再改检索代码。
2. 将错误码和型号归一化写成确定性纯函数。
3. 用Protocol让Service依赖能力而不是具体SDK。
4. 用Fake验证“应该调用”和“不应该调用”的分支。
5. 把引用身份交给Python，而不是交给LLM。
6. 将门控、Prompt和重排都写入版本字段或报告参数。
7. 分开报告候选、门控、回答和引用指标。
8. 对每轮优化保留独立报告，不覆盖旧结果。
9. 发现全局Prompt开始针对单题膨胀时及时回退。

## 11. 遗留问题

### 11.1 `q027` 跨文档关系召回

当前查询能够找到DM260清洁页面，但不能稳定联想到仓储工作站验收规程。后续可以考虑：

- 确定性的复合意图模板；
- 文档间关系元数据；
- 将“维护动作”和“验收动作”建立可检索关联；
- 学习型Cross-Encoder重排；
- 受控查询分解。

### 11.2 门控和模型拒答

`q007` 和 `q025` 说明有正确候选不等于最终回答。后续应分别校准门控与回答充分性判断，不能只调整一个全局相似度。

### 11.3 真实服务的不确定性

外部LLM即使使用 `temperature=0`，仍可能因服务端模型更新、推理实现或负载变化产生不同结果。长期评测应运行多轮，并报告均值、最差值和失败题稳定性。

### 11.4 生产能力缺口

系统仍缺少：

- OCR和复杂PDF版面解析；
- 用户认证、权限和租户隔离；
- 文档版本与删除审计；
- 后台摄取任务；
- 分布式向量数据库；
- 实时RCS、WMS和遥测工具；
- 生产级监控、速率限制和容量规划。

## 12. 最终结论

Week 3 已经完成从“能运行的RAG”到“能够定位失败、比较策略、控制证据、稳定降级并输出结构化诊断”的演进。

最终系统仍不是机器人控制器，也不能保证所有自然语言回答都正确，但它已经建立了关键工程边界：

- 检索有离线基线；
- 策略变化有可比指标；
- 无答案有确定性门控；
- LLM输出有Schema；
- 引用有真实Chunk白名单；
- 高风险动作有强制资质边界；
- 失败有稳定降级；
- 全链路有自动化测试和可审计报告。
