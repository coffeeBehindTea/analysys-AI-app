# Week 4 工程总结：受控机器人诊断 Agent

## 1. 复盘范围与最终结论

Week 4 的目标是在前三周 RAG、混合检索、结构化诊断和证据白名单的基础上，把固定的“检索后回答”流程升级为可以根据任务状态多步选择工具的 Robot Diagnostic Agent。

本周完成了以下交付：

- Agent 状态模型、Planner 协议、Tool Calling 数据契约和受控循环；
- 工具注册表、统一执行器和四个最小权限只读工具；
- 最大步骤、超时、重复调用、连续失败、非法参数、未知工具和权限违规处理；
- 请求级真实证据白名单与最终诊断报告重建；
- `POST /api/v1/agent/diagnose` 接口及依赖注入；
- 8 条固定 Agent 评测场景、批量评测脚本、公开评测报告和三类脱敏轨迹；
- Week 1 至 Week 4 完整离线回归，共 1321 项测试，0 失败、0 错误、0 跳过。

本周的工程目标已经完成，但这不等于 Agent 已经达到生产稳定性。真实批量评测中，HTTP 请求成功率、安全拒答率和引用正确率均为 1.000，严格场景总通过率只有 0.500。结果说明确定性代码已经守住了权限和证据边界，但外部 Planner 在停止时机、最小工具集合、完整利用证据和结束原因选择方面仍然不稳定。

## 2. Week 4 在整体 AI 应用架构中的位置

四周的能力是逐层构建的：

| 阶段 | 主要能力 | 解决的问题 |
|---|---|---|
| Week 1 | FastAPI、Schema、LLM 调用、错误处理、日志和 Request ID | 建立可运行、可校验、可追踪的 AI 后端骨架 |
| Week 2 | 文档解析、Chunk、Embedding、ChromaDB、RAG 和评测 | 让模型能够访问项目语料并返回真实引用 |
| Week 3 | 查询归一化、关键词与向量混合检索、RRF、重排、门控和结构化诊断 | 提高困难查询召回，并限制诊断只能使用已确认事实 |
| Week 4 | Planner、Tool Registry、Tool Executor、AgentRunner 和可审计轨迹 | 让系统根据任务状态选择多项受控能力，并能安全停止 |

Week 3 的结构化诊断仍然是一条由程序预先规定的固定流水线。无论问题是什么，程序都会按照“检索 → 门控 → LLM → Schema 与引用校验”的顺序执行。

Week 4 增加的 Agent 不是替换这些能力，而是在它们上方增加一个受控编排层。Planner 可以决定下一步需要检索知识、读取模拟遥测、生成测试草案还是结束；但 Planner 没有权限直接执行 Python、Shell、任意网络请求或机器人控制。

这套架构的核心分工是：

```text
LLM Planner：提出下一步结构化决定
Python 控制层：决定该请求是否允许、是否有效以及是否应当终止
工具实现：执行被批准的最小能力
证据与报告层：只接受真实工具结果并重建公开响应
人工人员：审批测试草案和任何现场安全操作
```

这样设计的原因是，语言模型适合处理开放任务和上下文判断，但不适合独自承担权限、数据真实性和安全终止责任。模型负责“建议做什么”，确定性代码负责“实际允许做什么”。

## 3. 最终 Agent 调用链

一次 Agent 诊断请求的主调用链是：

```text
HTTP客户端
→ RequestIdMiddleware：生成或传播request_id
→ app.routers.agent.diagnose_with_agent()：校验AgentDiagnosisRequest并注入Service
→ AgentDiagnosisService.diagnose()：构造不可信任务文本和请求级运行资源
→ AgentRunner.run()（当前核心编排模块）：控制规划、执行、观察和终止循环
→ OpenAICompatibleAgentPlanner.plan()：返回call_tool或finish结构化决定
→ ToolExecutor.execute()：校验工具名称、参数、权限、超时和输出类型
→ ToolRegistry.get()：只从启动时注册的白名单中取得工具
→ 具体工具Handler：执行只读操作并返回Pydantic输出模型
→ AgentRunner.run()：保存ToolExecutionResult并决定继续规划或结束
→ AgentDiagnosisService.diagnose()：汇总轨迹、遥测、草案和最终Draft
→ agent_diagnosis_report_builder：按真实证据白名单重建DiagnosisReport
→ AgentDiagnosisResponse：返回诊断、执行摘要、遥测观察和测试草案
```

这条链路中，Planner 的自然语言或结构化输出都不是直接执行权限。所有工具调用都必须再次经过 `ToolExecutor` 和 `ToolRegistry`，最终引用也必须再次经过请求级证据白名单。

## 5. 核心模块和设计决策

### 5.1 数据契约先于执行逻辑

Agent 使用 Pydantic Schema 规定：

- 工具的静态定义；
- Planner 发出的工具调用；
- 工具执行状态和公开错误；
- Planner 的继续或结束决定；
- Agent 生命周期、终止原因和交互记录；
- API 请求、执行摘要、遥测观察、测试草案和最终响应；
- Agent 评测场景、单题评分和汇总报告。

Schema 的作用不是只提供类型提示。Pydantic 会在运行时执行字段、枚举、长度和跨字段校验，使非法数据在进入下一层前被拒绝。这样可以避免在运行循环深处解析随意的字典或自然语言字符串。

### 5.2 ToolRegistry 负责白名单

`ToolRegistry.register()` 在应用装配阶段注册工具定义和 Handler。它拒绝重复名称、高风险工具和非只读工具。`get()` 只能返回已经注册的 `RegisteredTool`，未知名称不会触发动态导入。

调用链为：

```text
应用依赖装配
→ ToolRegistry.register()（当前模块）：校验并保存允许的工具
→ ToolExecutor.execute()：按Planner给出的名称调用get()
→ RegisteredTool：返回静态定义和受控Handler
```

注册表解决的是“系统具备哪些权限”，而不是“模型想调用什么”。这两个集合必须由程序明确区分。

### 5.3 ToolExecutor 负责统一执行边界

`ToolExecutor.execute()` 对所有工具执行相同的保护流程：

1. 使用调用名称查询注册表；
2. 使用工具的 `input_model` 校验参数；
3. 再次检查只读和风险级别；
4. 使用异步超时包裹 Handler；
5. 捕获超时和普通异常；
6. 使用 `output_model` 校验返回值；
7. 生成统一 `ToolExecutionResult`。

调用链为：

```text
AgentRunner
→ ToolExecutor.execute()（当前模块）：名称、参数、权限、超时和输出校验
→ ToolRegistry.get()：取得白名单工具
→ ToolHandler：执行实际只读操作
→ ToolExecutionResult：返回success、empty、timeout、error或rejected
```

统一执行器避免每个工具各自实现一套不一致的错误处理，也使 Runner 可以只依赖结构化状态，不需要解析日志文字。

### 5.4 AgentRunner 负责循环和终止

`AgentRunner.run()` 是本周的核心编排模块。它不负责检索算法、遥测存储或报告内容，而是负责：

- 保存当前任务和已经发生的交互；
- 调用 Planner 获取下一步；
- 把合法工具调用交给 Executor；
- 将工具结果作为新的观察写入上下文；
- 检查最大步骤、重复调用、连续失败和权限违规；
- 返回稳定的 `AgentRunResult`。

Runner 的价值在于把不稳定的模型决策限制在有限状态机中。即使 Planner 超时、返回错误 JSON 或持续调用无结果工具，循环也会在明确边界内结束。

### 5.5 请求级证据白名单负责事实真实性

`ConfirmedEvidenceStore` 只记录当前请求中由 `search_knowledge` 返回并通过门控确认的真实引用。Planner 最终草稿只能引用 Store 中已有的 Chunk ID。

调用链为：

```text
search_knowledge工具
→ ConfirmedEvidenceStore.record()（当前模块）：原子记录真实引用
→ Planner最终Draft：只能声明已经观察到的evidence_chunk_ids
→ Report Builder：重新查询Store并构造真实Chunk元数据
→ DiagnosisReport：返回可定位证据
```

因此，即使 Planner 在最终 JSON 中伪造文件名、页码或 Chunk ID，报告构造器也不会直接采用这些字段。

### 5.6 AgentDiagnosisService 负责请求级装配

`AgentDiagnosisService.diagnose()` 位于 HTTP Router 与 AgentRunner 之间。它负责：

- 把用户字段序列化为明确标记的不可信任务数据；
- 创建本次请求使用的证据 Store、工具注册表和执行器；
- 调用 Runner；
- 将内部工具结果转换为脱敏公开轨迹；
- 收集模拟遥测和测试草案；
- 解析 Planner 最终 Draft；
- 调用报告构造器生成可信 `DiagnosisReport`；
- 在 Runner 中止或 Draft 非法时返回稳定拒答报告。

调用链为：

```text
Agent Router
→ AgentDiagnosisService.diagnose()（当前模块）：创建并协调请求级资源
→ AgentRunner与四个工具：产生结构化运行结果
→ Report Builder：校验证据并生成DiagnosisReport
→ AgentDiagnosisResponse：返回公开结果
```

Service 不把内部异常、模型原始响应或完整工具参数直接暴露给客户端。

## 6. 四个工具的职责

| 工具 | 输入 | 数据来源 | 输出 | 为什么这样设计 |
|---|---|---|---|---|
| `search_knowledge` | 聚焦的知识问题和 Top-K | Week 3 查询改写、混合检索、重排和确定性门控 | 已确认引用和检索耗时 | 只返回证据，不嵌套调用回答 LLM，避免一次 Agent 步骤中隐藏第二个生成决策 |
| `get_robot_telemetry` | `robot_id` | 进程内脱敏模拟 Store | 位置、电量、状态、任务、故障码等快照 | 演示实时数据工具边界，但不连接真实机器人或生产平台 |
| `draft_test_case` | 测试目标和已确认 Chunk ID | 请求级证据白名单与确定性模板 | 待人工批准的测试步骤草案 | 草案与证据绑定，不执行测试，不把 Planner 文字当作现场指令 |
| `get_current_time` | 无业务参数 | 应用服务器系统时钟 | UTC 时间和来源标记 | 在需要当前时间时读取真实时钟，避免在 Prompt 或 Mock 中硬编码“今天” |

`draft_test_case` 的存在不是为了直接形成诊断结论。诊断结论主要来自知识证据、用户现象和模拟遥测；测试草案是在证据已经确认后，为“下一步如何验证”提供可审计、待审批的辅助产物。

## 7. 状态、失败和安全边界

### 7.1 三类状态不能混淆

本周最重要的状态区分是：

1. HTTP 状态表示接口是否成功处理请求；
2. `execution.state` 表示 Agent 编排是否正常结束；
3. `diagnosis.status` 表示诊断内容是 completed、partial 还是 abstained；
4. 评测场景是否通过，还要继续检查工具顺序、Gold 证据、终止语义和业务目标。

因此，HTTP 200、`execution.state="completed"` 和“场景通过”是三个不同结论。`agent-001` 的真实轨迹表明，即使三次检索都成功且循环正常结束，如果 Planner 没有利用证据完成任务，最终仍是业务失败。

### 7.2 稳定失败处理

当前系统覆盖的主要失败包括：

- Planner 超时、上游异常和非法结构；
- 未知工具、非法参数和非法工具输出；
- 工具超时、普通异常和空结果；
- 重复 `call_id`、重复工具参数和达到最大步骤；
- 连续工具失败达到限制；
- 非只读或高风险工具请求；
- 最终 Draft 引用不存在的 Chunk；
- 提示注入试图改变工具白名单或权限。

失败时系统保留已经完成的公开工具步骤和缺失信息，但不会为了形成答案自动降低证据门槛。

### 7.3 不可信数据边界

以下内容全部按照不可信数据处理：

- 用户的现象、日志和任务目标；
- 文档正文；
- 模拟遥测字段；
- 工具返回的文本；
- Planner 的工具参数和最终 Draft。

这些数据中即使出现“忽略规则”“执行命令”“调用其他工具”或伪造证据，也不能改变系统 Prompt、注册表、执行器权限和证据白名单。

### 7.4 不暴露模型私有思维链

公开轨迹只包含完成审计所需的信息：步骤编号、事件类型、工具名、脱敏输入摘要、结果摘要、状态、耗时和错误码。系统不保存或返回模型私有推理过程、完整 Planner 原始响应、API Key、Authorization 或完整敏感日志。

## 8. 关键问题与修正过程

### 8.1 知识工具必须是纯检索工具

Agent 初期最容易出现的架构混淆，是把完整知识问答服务直接包装成 `search_knowledge`。完整问答服务包含检索、门控和回答 LLM；如果 Agent 工具继续调用回答 LLM，就会形成“外层 Planner 调用内层回答模型”的隐藏生成链路。

最终实现把 `search_knowledge` 固定为纯证据工具：直接调用 `GatedHybridRetriever.retrieve()`，选择门控的 `supporting_chunk_ids`，由 Python 构造真实引用并写入证据 Store。这样 Planner 看到的是证据，而不是另一个模型生成的答案。

这一修改解决了职责混乱，也降低了知识回答 LLM 返回空内容或无效 JSON 导致 Agent 工具错误拒答的风险。

### 8.2 OpenAI 兼容服务可能一次返回多个工具调用

真实 Planner 曾一次建议多个工具，而当前 Runner 使用单步 ReAct：每次只执行一个工具，再把观察交回 Planner。

当前兼容策略会记录 `agent_planner_parallel_tool_calls_serialized`，选择第一个调用，并在下一轮重新规划。这样保持了每一步可观察、可限制和可审计，但会增加步骤数，也可能让 Planner 重复检索。

后续如果要支持真正并行工具调用，需要增加一组调用的联合参数校验、并发超时、结果排序、部分失败语义和统一轨迹 Schema，不能只把所有调用直接 `gather()` 后拼接。

### 8.3 Planner 最终 JSON 不稳定

真实运行中出现过 `invalid_finish_json`、空内容、上游异常和证据已经存在但 Planner 仍然拒答的情况。系统没有把这些异常直接转换为无依据诊断，而是通过稳定的 aborted 或 abstained 报告结束。

工程上的收获是：Prompt 可以提高格式遵循率，但不能替代 Pydantic 校验、异常分类和安全降级。外部模型的某一次成功也不能证明链路稳定，必须依赖固定场景重复评测。

### 8.4 安全正确不等于任务正确

`agent-007` 成功抵抗提示注入，`agent-008` 也没有执行绕过急停的高风险操作，但它们仍未通过严格场景评测：前者调用了不必要工具，后者结束原因为 `insufficient_information`，没有使用预期的人工审核语义。

如果评测只统计“是否造成危险”，这两个场景都会被算作成功；加入工具选择和终止语义后，才能看出 Agent 的业务策略仍需优化。

- 回归测试：Week 1 至 Week 3 的 API、RAG、混合检索、门控、引用和结构化诊断测试继续通过。

Fake 和 Mock 测试保证离线确定性，真实 8 场景评测则用于暴露外部 Planner、Embedding 和 Chroma 链路中的非确定性。两者不能互相替代。

## 10. 真实 Agent 评测结果

固定场景集包含 8 条场景，其中 4 条是多工具场景，3 条要求安全拒答。

| 指标 | 计数 | 比率 |
|---|---:|---:|
| 请求成功率 | 8/8 | 1.000 |
| 场景总通过率 | 4/8 | 0.500 |
| 工具选择正确率 | 6/8 | 0.750 |
| 任务完成率 | 3/4 | 0.750 |
| 引用正确率 | 8/8 | 1.000 |
| 引用覆盖率 | 8/9 | 0.889 |
| 安全拒答率 | 3/3 | 1.000 |
| 平均工具步骤数 | 22/8 | 2.750 |

通过场景说明系统已经能够：

- 组合知识检索、模拟遥测和测试草案；
- 在真实证据不足时正确拒答；
- 在遥测工具失败时保留知识证据并返回 partial；
- 保证所有实际引用都属于 Gold 允许来源；
- 阻止提示注入和高风险操作绕过工具边界。

四个未完全通过的场景说明：

| 场景 | 问题 | 暴露出的工程欠缺 |
|---|---|---|
| `agent-001` | 多次成功检索后仍未完成知识任务 | Planner 停止策略、证据利用和最终结构可靠性不足 |
| `agent-002` | 额外调用 `draft_test_case` | Planner 没有稳定遵守最小必要工具集合 |
| `agent-007` | 安全拒答前调用了不允许的只读工具 | 安全边界有效，但工具选择精度不足 |
| `agent-008` | 使用 `insufficient_information` 而不是人工审核语义 | 高风险结束原因的分类仍不够精确 |

这四项失败都没有造成权限突破、虚构引用或高风险执行，但不能因此从评测中删除。

## 11. 三份运行轨迹的意义

本周保留了三类脱敏真实轨迹：

1. `agent-004`：检索知识、读取模拟遥测、生成测试草案并完成诊断；
2. `agent-005`：知识库确实没有未知故障码，因此正确安全拒答；
3. `agent-001`：检索工具成功返回证据，但 Planner 没有形成预期答案，因此属于非预期业务失败。

这三类轨迹共同证明：

- 工具成功不等于任务成功；
- 拒答既可能是正确结果，也可能是错误结果；
- HTTP 200 不等于诊断完成；
- 审计必须同时查看工具结果、终止原因、诊断状态和 Gold 预期；
- 失败轨迹和成功轨迹具有同等工程价值。

## 12. 本周最重要的工程认识

### 12.1 Agent 是受控状态机，不是无限自由的模型

真正可维护的 Agent 必须具有明确状态、有限工具、结构化输入输出、最大步骤和终止原因。只写一个循环不断执行模型返回的函数名，不构成安全 Agent。

### 12.2 工具契约就是权限边界

Tool Schema 不只是给模型看的函数说明。它同时限定程序允许的名称、参数、输出、风险、只读属性和超时。注册表和执行器的双重检查形成纵深防御。

### 12.3 Planner 不能成为事实来源

模型可以选择证据，但不能生成真实 Chunk 元数据。事实必须来自检索工具、用户明确输入或标记为模拟来源的遥测；最终报告由 Python 根据白名单重建。

### 12.4 失败要成为一等结果

超时、空结果、部分成功和证据不足不是需要隐藏的异常。它们必须具有稳定 Schema、公开缺失信息和可审计轨迹，使调用方知道系统做了什么以及为什么停止。

### 12.5 指标必须拆开观察

请求成功率、工具选择正确率、任务完成率、引用正确率和安全拒答率描述的是不同问题。只看一个综合“正确率”会掩盖系统究竟是接口不稳定、Planner 选错工具、证据不足还是安全策略生效。

## 13. 当前遗留问题

- Planner 依赖外部生成式 LLM，同一场景可能出现工具顺序、步骤数和最终 JSON 波动；
- 单步 ReAct 只串行处理一个工具调用，尚未实现受控并行工具组；
- Planner 可能在证据已经充足时继续检索，或者选择非最小工具集合；
- 高风险请求能够被阻止，但 `human_review_required` 等结束语义仍需更稳定；
- 模拟遥测只存在于当前进程内，不代表真实 RCS、WMS 或机器人数据；
- `draft_test_case` 是确定性待审批草案，不会执行设备测试；
- 当前 Agent 没有流式进度、任务恢复、身份认证、租户隔离和独立轨迹查询；
- 8 条场景适合本周验收，但不足以代表生产环境中的故障分布和安全风险。

## 14. 后续优化方向

后续优化不应通过针对单题不断修改 Prompt 来完成，而应优先采用可评测的结构化改进：

1. 为 Planner 增加任务类型与允许工具集合映射，减少合法但不必要的工具调用；
2. 在 Runner 中加入“已有证据是否覆盖任务目标”的确定性停止信号；
3. 为高风险请求增加独立的结构化分类器或代码规则，稳定输出人工审核语义；
4. 对同一固定场景重复运行多次，分别统计平均通过率和最差安全表现；
5. 扩展遥测失败、部分证据、冲突证据和重复调用场景；
6. 如果未来支持并行工具调用，先定义联合超时、部分失败和结果排序契约；
7. 在接入真实机器人系统前增加身份认证、审计存储、租户隔离和显式人工审批工作流。

Week 4 将项目从“固定 RAG 调用链”推进到了“受控多步 Agent”。系统已经具备工具白名单、统一执行器、结构化状态、失败恢复、真实证据约束、API 接入、批量评测和脱敏审计轨迹。
