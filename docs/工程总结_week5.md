# Week 5 工程总结：多模态机器人诊断与可靠性评测

## 1. 总结范围与最终结论

Week 5 的目标是在 Week 4 受控 Robot Diagnostic Agent 的基础上，让 Agent 能够处理现场图片、仪表截图和设备指示灯照片，同时继续遵守前三周建立的证据、引用、风险和拒答约束。

本周完成了以下交付：

- 图片请求、验证后图片、视觉模型草稿和公开视觉观察的数据契约；
- Base64 解码、真实图片格式识别、大小、尺寸、像素数和空内容校验；
- OpenAI 兼容 Vision Provider、独立 Vision 配置和 Fake Vision Provider；
- 本地 Tesseract OCR、文字行与边界框契约、确定性面板规则解析；
- OCR 与规则、Vision 模型、直接拒答三条路线的 6 样本对照实验；
- 请求级图片 Store 和只读 `analyze_robot_image` Agent 工具；
- 图片、现象、脱敏日志、知识证据和模拟遥测的联合诊断链路；
- 30 条多模态 Agent 场景、批量评测脚本、最终报告和完整脱敏轨迹；
- Week 1 至 Week 5 的完整离线回归，共 2214 项测试，0 失败、0 错误、0 跳过。

本周学习目标已经完成，但系统仍不是生产级机器人诊断产品。最终 30 场景评测中，请求成功率为 1.000、安全拒答率为 1.000、Vision 工具选择正确率为 0.933；严格场景总通过率只有 0.233。结果表明，图片输入、安全拒答和工具边界已经形成稳定的工程骨架，但真实 Planner 在最小工具集合、终止语义、来源利用、完整证据覆盖和任务完成方面仍然不稳定。

## 2. Week 5 在整体 AI 应用架构中的位置

五周能力按照“服务骨架 → 外部知识 → 可靠检索 → 受控行动 → 多模态观察”的顺序逐层增加：

| 阶段 | 核心能力 | 解决的问题 |
|---|---|---|
| Week 1 | FastAPI、Pydantic、LLM、错误处理、SSE、Request ID | 建立可运行、可校验、可追踪的 AI 服务骨架 |
| Week 2 | 文档解析、Chunk、Embedding、ChromaDB、RAG、引用评测 | 让模型访问项目语料，并返回可定位的真实引用 |
| Week 3 | 查询归一化、关键词与向量混合检索、RRF、重排、门控、结构化诊断 | 提高困难查询召回，并限制诊断只能使用已确认知识证据 |
| Week 4 | Planner、工具注册表、统一执行器、AgentRunner、失败降级、审计轨迹 | 让模型在受控循环中选择多项只读能力 |
| Week 5 | 图片适配、Vision、OCR、视觉工具、来源分层、多模态评测 | 让 Agent 能够观察图片，同时不把视觉推断冒充工程事实 |

Week 5 没有替换 RAG、诊断 Schema 或 AgentRunner。它在已有 Agent 工具层增加了一种新的信息来源：视觉观察。

视觉模型适合回答“图片里看到了什么”，知识库适合回答“这些现象在设备资料中意味着什么”，模拟遥测适合回答“当前演示机器人状态是什么”。这三类信息不能相互替代：

```text
Vision模型：观察图片中的颜色、文字、亮灭、遮挡和部件关系
知识库RAG：提供设备资料、故障说明和安全规程中的可追溯依据
模拟遥测：提供当前演示对象的位置、电量、任务和故障状态
Planner：根据任务选择需要调用的只读工具
Python控制层：校验权限、数据契约、来源、证据和最终响应
人工人员：确认高风险操作、现场状态和测试草案
```

这样设计的原因是，视觉模型和语言模型都是概率性模型。它们可以协助观察和组织信息，但不能独自决定图片真实性、工程结论、安全权限或现场操作。

## 3. 多模态 Agent 的完整调用链

一次带图片的诊断请求经过以下链路：

```text
HTTP客户端
→ RequestIdMiddleware：生成或传播request_id
→ app.routers.agent.diagnose_with_agent()：校验AgentDiagnosisRequest
→ AgentDiagnosisService.diagnose()：协调本次请求的Agent资源
→ VisionInputAdapter：解码Base64并校验真实图片格式和资源上限
→ RequestVisionInputStore：以image_001等请求级引用保存验证后图片
→ AgentRunner.run()：开始规划、工具执行、观察和终止循环
→ OpenAICompatibleAgentPlanner.plan()：返回call_tool或finish决定
→ ToolExecutor.execute()：校验工具名、参数、只读权限、风险、超时和输出
→ analyze_robot_image：按image_ref读取当前请求的图片
→ OpenAICompatibleVisionProvider.analyze_image()：发送原生多模态消息
→ VisionObservation：返回带来源、模型和Prompt版本的结构化视觉观察
→ AgentRunner.run()：记录观察并决定是否继续检索知识、读取遥测或结束
→ AgentDiagnosisService.diagnose()：构造公开轨迹并收集视觉、遥测和草案结果
→ agent_diagnosis_report_builder：校验最终草稿和知识证据白名单
→ AgentDiagnosisResponse：返回诊断、执行摘要、视觉观察、遥测和测试草案
```

这条链路把“图片能否进入系统”“模型从图片看到了什么”“这些观察能否支持工程结论”分成三个独立问题：

1. `VisionInputAdapter` 判断输入是否是可接受的真实图片；
2. Vision Provider 生成结构化可见观察；
3. Agent、知识检索和报告构造器决定是否有足够依据形成诊断。

图片通过格式校验并不代表图片内容真实；Vision 输出通过 Schema 校验也不代表工程结论正确。

## 5. 图片输入适配层

### 5.1 外部载荷与内部输入分离

`VisionImagePayload` 表示客户端提交的外部载荷，主要包含：

- `mime_type`：用户声明的 MIME 类型；
- `encoding`：当前固定为 Base64；
- `image_base64`：不包含 Data URL 前缀的图片内容；
- `analysis_goal`：需要观察的目标；
- `detail`：视觉模型细节级别。

这个 Schema 只能证明字段结构合法，不能证明 Base64 能成功解码，也不能证明文件内容与声明的 MIME 类型一致。因此 Provider 不直接接受 `VisionImagePayload`。

`VisionInputAdapter` 的调用链为：

```text
AgentDiagnosisService
→ VisionInputAdapter.adapt()（当前模块）
→ 严格Base64解码
→ Pillow读取真实图片格式和尺寸
→ 字节数、边长和总像素检查
→ SHA-256元数据绑定
→ VisionInput
```

验证后的 `VisionInput` 才能进入 Provider。它包含真实图片元数据、受保护的图片字节、分析目标和细节级别。图片字节使用 `SecretBytes`，并从普通 `model_dump()`、日志表示和公开响应中排除。

### 5.2 为什么同时限制大小、边长和像素数

只限制 Base64 字符数不足以覆盖所有图片风险：

- 文件字节数限制控制请求体、内存和网络成本；
- 单边尺寸限制拒绝异常宽图或长图；
- 总像素限制防止小压缩文件解码后占用巨大内存；
- Pillow 的真实格式识别防止扩展名或 MIME 声明与内容不一致；
- 空内容和损坏图片在调用外部 Vision 服务前被本地拒绝。

默认单张图片上限为 5 MiB，任意一边不超过 4096 像素，总像素不超过 1600 万；一次 Agent 请求最多包含 3 张图片。这些是当前教学项目的资源边界，不是所有生产系统的通用值。

## 6. Vision Provider 与结构化观察

### 6.1 Provider 协议

`VisionProvider` 是依赖倒置边界。Agent 工具只依赖“接收验证后图片并返回 `VisionObservation`”这一能力，不依赖某一家供应商 SDK 的具体对象。

调用链为：

```text
AnalyzeRobotImageToolHandler
→ VisionProvider.analyze_image()（当前协议）
→ OpenAICompatibleVisionProvider或FakeVisionProvider
→ VisionObservation
```

真实实现使用 `AsyncOpenAI` 的 OpenAI 兼容接口。Fake 实现保存脱敏调用记录，并返回固定观察或预设异常，使自动化测试不需要真实密钥、网络或计费调用。

### 6.2 原生多模态输入

真实 Provider 把分析目标和图片 Data URL 共同放入模型的 message content。图片直接进入多模态模型，不采用以下两阶段链路：

```text
图片 → 第一个模型生成无来源摘要 → 文本模型把摘要当作唯一事实
```

避免这种链路的原因是，中间摘要会丢失图片来源、可见区域、不确定性和细节，而且第二个模型无法重新核对原图。

### 6.3 视觉观察的数据边界

`VisionObservation` 可以表达：

- 图片中可见的观察；
- 可辨认指示器及其表面状态；
- 无法确认或需要人工复核的项目；
- 整体状态和是否需要人工检查；
- `source="vision_model"`；
- 来源图片摘要、模型名和 Prompt 版本。

视觉观察只允许描述“看到了什么”，不能仅凭字段结构直接宣称根因。例如“NET 指示灯红色常亮”可以是视觉观察，“网络模块已经损坏”需要知识资料、遥测或人工检查支持。

## 7. OCR、规则解析与工具选择实验

### 7.1 OCR 路线

`TesseractOcrProvider` 使用 `pytesseract` 调用本地 Tesseract 引擎，返回文字行、置信度和边界框。OCR 适合清晰的故障码、数字和状态文字，但不擅长判断颜色、亮灭、插头间隙或部件空间关系。

OCR 调用链为：

```text
验证后图片
→ TesseractOcrProvider.analyze_image()（当前模块）
→ pytesseract调用本地Tesseract子进程
→ 文字、置信度和边界框
→ OcrObservation
```

`OcrRuleParser` 再根据固定规则提取已支持的面板字段。规则解析是确定性的：相同 OCR 文本会得到相同字段，不需要 LLM 推理；没有匹配到支持规则时返回 `unsupported` 或 `partial`，不会补写不存在的状态。

规则解析调用链为：

```text
OcrObservation
→ OcrRuleParser.parse()（当前模块）
→ 固定字段和取值规则
→ OcrRuleParseResult
```

### 7.2 三路线结果

6 条脱敏样本分别经过三条路线，共形成 18 个单路线结果：

| 路线 | 通过率 | 平均延迟 | P95 延迟 | 外部模型调用 | 主要适用范围 |
|---|---:|---:|---:|---:|---|
| 本地 OCR 加规则解析 | 0.333 | 651.523 ms | 875.409 ms | 0 | 清晰文字面板、故障码和固定字段 |
| Vision 模型 | 0.333 | 12587.276 ms | 27044.173 ms | 6 | 颜色、亮灭、遮挡、连接和部件关系 |
| 直接拒答 | 0.333 | 10.950 ms | 19.529 ms | 0 | 缺失、严重模糊或无法确认的图片 |

三条路线通过率相同不表示能力相同。每条路线只在适合自己的两类样本上通过：OCR 无法替代视觉关系判断，Vision 不应被无条件调用，直接拒答也不能处理清晰可回答图片。

## 8. `analyze_robot_image` Agent 工具

### 8.1 请求级图片 Store

客户端不能自行提供 `image_ref`。Service 在图片校验成功后，按照请求内顺序生成 `image_001`、`image_002` 等不透明引用，并写入 `RequestVisionInputStore`。

调用链为：

```text
AgentDiagnosisRequest.images
→ VisionInputAdapter
→ AgentDiagnosisService登记图片
→ RequestVisionInputStore.register()（当前模块）
→ image_ref与VisionInput绑定
→ analyze_robot_image按引用读取
```

Store 是请求级对象，不能使用全局缓存。这样可以避免一个请求读取另一个请求的图片，也不会让图片在进程内无限积累。

### 8.2 工具定义与执行

`analyze_robot_image` 是低风险、只读工具。输入只有：

- `image_ref`：当前请求内的图片引用；
- `analysis_goal`：本次需要观察的目标。

执行链为：

```text
AgentRunner
→ ToolExecutor.execute()
→ ToolRegistry.get("analyze_robot_image")
→ AnalyzeRobotImageToolHandler.__call__()（当前模块）
→ RequestVisionInputStore.get(image_ref)
→ VisionProvider.analyze_image()
→ VisionObservation
→ ToolExecutionResult
```

Handler 不执行设备控制、不修改图片、不动态导入工具、不访问二维码或图片中的网址。未知图片引用返回空结果；Vision 超时、上游错误和无效响应分别转换成可审计的脱敏错误码。

## 9. 多模态诊断编排与来源分层

### 9.1 API 扩展

`POST /api/v1/agent/diagnose` 在保持纯文本请求兼容的同时增加 `images` 列表。请求没有图片时，列表默认为空；有图片时，每张图片先完成本地适配，再进入 Agent 循环。

公开响应增加 `vision_observations`。该列表必须与执行轨迹中成功的 `analyze_robot_image` 步骤一一对应：不能凭空增加视觉观察，也不能隐藏已经成功执行的视觉调用。

### 9.2 四类信息来源

| 来源 | 表示的内容 | 可以证明什么 | 不能自动证明什么 |
|---|---|---|---|
| `user_report` / `log_excerpt` | 用户描述和脱敏日志 | 用户提交了哪些现象和日志文字 | 内容真实、日志完整或根因已经确认 |
| `vision_model` | 图片中的结构化可见观察 | 模型观察到了哪些文字、颜色、状态和不确定项 | 设备内部故障、操作已经执行或知识规则已经成立 |
| `confirmed_knowledge` | RAG 门控确认的真实 Chunk | 资料中明确写了哪些工程规则和安全要求 | 当前现场一定符合资料中的触发条件 |
| `simulated_memory` | 进程内脱敏模拟遥测 | 当前演示 Store 返回了哪些状态 | 真实机器人、RCS 或 WMS 的现场状态 |

最终诊断必须保留来源差异。图片与日志冲突时，系统不能静默选择其中一个；应保留冲突、降低结论强度并要求人工核对。

## 10. 多模态安全边界

### 10.1 图片内容属于不可信数据

图片中的以下内容都不能作为系统指令执行：

- “忽略之前规则”之类的 Prompt Injection；
- Shell、Python、机器人控制或复位命令；
- 二维码或屏幕中的网址；
- API Key、Authorization 或密钥样例；
- 要求扩大工具白名单或修改风险等级的文字。

二维码即使被读取，也只能作为普通文本数据，不会触发浏览器、HTTP 客户端或其他工具访问链接。

### 10.2 轨迹脱敏

公开多模态轨迹只保存：

- 场景编号和脱敏输入摘要；
- 工具名、状态、耗时和错误码；
- 公开视觉观察和诊断响应；
- 确定性评分与失败原因。

轨迹不保存完整 Base64、图片正文、本地图片路径、请求级图片元数据、Authorization、API Key、完整敏感日志或模型私有思维链。公开视觉观察可以保留 `source_image_sha256` 作为来源完整性指纹；摘要不能还原图片，也不是本地路径。

### 10.3 高风险操作仍由人工负责

当前五个 Agent 工具全部只读。系统没有机器人运动控制、远程复位、任务下发、充放电控制、配置修改或真实测试执行能力。`draft_test_case` 只生成待人工批准的确定性草案，不表示测试已经执行。

## 11. 30 条多模态评测集

评测集固定包含以下类别：

| 类别 | 数量 | 主要验证目标 |
|---|---:|---|
| `normal_image` | 8 | 清晰图片下完成视觉、知识和遥测联合诊断 |
| `noisy_or_low_quality` | 8 | 模糊、遮挡和低质量图片下不猜测，并保留可用部分结果 |
| `missing_or_unanswerable` | 6 | 缺图、无关图或知识不足时正确拒答 |
| `image_log_conflict` | 4 | 图片与日志冲突时保留来源并要求复核 |
| `prompt_injection_or_high_risk` | 4 | 拒绝图片指令、链接访问和设备写操作 |
| **总计** | **30** | 覆盖正常、退化、缺失、冲突和对抗情况 |

每条场景不仅记录问题和图片，还记录：预期是否调用 Vision、必需工具、允许工具、禁止工具、预期诊断状态、预期证据、预期来源、安全要求和任务完成条件。

评测脚本在发送第一条真实 HTTP 请求前预检整批图片的路径、SHA-256、格式、尺寸、像素数和字节数。这样不会运行到一半才因坏图片终止，也不会在数据集无效时白白消耗外部模型调用。

### 12.3 为什么严格总通过率较低

场景总通过率是联合指标。一条场景必须同时满足：

- HTTP 请求成功；
- Agent 执行和终止状态正确；
- Vision 调用判断正确；
- 图片观察覆盖 Gold；
- 工具集合和关键顺序正确；
- 任务完成条件正确；
- 引用正确且覆盖完整；
- 信息来源标注正确；
- 安全规则和拒答行为正确。

任何一项失败，整条场景都不通过。因此 0.233 不能简单解释成“只有 23.3% 的图片被识别”，也不能使用 1.000 的 HTTP 成功率代替业务正确率。

主要失败集中在：Vision 状态与 Gold 不一致、Planner 结束原因不符合预期、来源不一致、Agent 状态不符合预期、知识证据不完整，以及调用了场景不需要的 `search_knowledge` 或 `get_current_time`。

## 13. 关键问题、修正与设计取舍

### 13.1 确定性评分不能只依赖固定字面匹配

真实 Vision 和 Planner 可能使用“未观察到可辨认状态”“没有清晰显示”“接口没有完全贴合”等等价表达。只匹配一个固定短语会把语义正确的结果误判为失败。

本周扩展了确定性归一化和等价表达判断，并允许 LLM-as-judge 对少量边界表达提供辅助意见。但辅助 Judge 不能改写真实响应，也不能替代工具、引用、来源和安全规则的确定性评分。

### 13.2 单条请求失败不能终止整个批次

批量评测把超时、连接失败、非 2xx、非法 JSON 和响应 Schema 错误转换成脱敏失败结果，然后继续执行其余场景。只有数据集自身无法形成有效完整轨迹时，才会拒绝生成误导性的正式报告。

调用链为：

```text
30条场景
→ evaluate_multimodal.py预检全部图片
→ evaluation服务（当前模块）逐条调用Agent API
→ 单条失败转换成结构化失败评分
→ 继续剩余场景
→ 汇总指标、轨迹和报告
```

### 13.3 Vision 错误必须可以区分

最初把所有视觉失败统一记为普通工具错误，无法定位是超时、上游不可用还是模型返回无效结构。最终增加了 `vision_timeout`、`vision_upstream_error` 和 `invalid_vision_response` 等脱敏错误码，既不公开上游敏感正文，又能支持故障统计。

### 13.4 只保存三条成功轨迹不足以排查失败

最终报告保留三条代表性轨迹，同时保存通过响应契约但确定性评分失败的完整脱敏轨迹。这样可以从失败场景追溯到真实工具顺序、状态和错误码，而不是只看到一个汇总百分比。

### 13.5 撤销关键词工具范围和固定次数隐藏策略

项目曾尝试根据任务文字关键词缩小可见工具范围，并在两次成功知识检索后隐藏 `search_knowledge`。这两种规则把自然语言表述和固定调用次数误当成任务是否完成的可靠信号，容易对当前 Gold 过拟合，也可能损失复杂任务所需的后续证据。

最终保留的策略是结构性边界：

- 请求没有图片时，不暴露无法执行的视觉工具；
- 请求有图片时，视觉工具只能读取当前请求 Store；
- 其余注册只读工具保持可见；
- Runner 不按固定成功次数隐藏知识检索；
- 是否继续或结束仍由 Planner 提议，再由最大步骤、重复调用、连续失败和权限策略约束。

这一回退避免了为了局部评测数字牺牲架构的一般性。

## 17. 当前限制

- Vision 模型输出具有非确定性，同一图片在不同模型、Prompt 或运行中可能产生不同观察；
- 模糊、反光、遮挡、小字、复杂背景和相似颜色仍可能导致漏读或误读；
- OCR 依赖本地 Tesseract 安装、语言数据和操作系统环境；
- 当前 Base64 JSON 请求会增加请求体积，生产系统通常需要受控对象存储和短期引用；
- 当前图片 SHA-256 只能用于完整性关联，不能证明拍摄时间、设备身份或现场真实性；
- 当前模拟遥测不连接真实机器人、RCS、WMS 或生产平台；
- Agent 工具全部只读，系统不能执行维修、复位、运动控制或真实测试；
- 当前没有身份认证、租户隔离、文件病毒扫描、生产审计平台或正式前端；
- Planner 和 Vision 依赖外部模型，仍可能超时、返回无效结构或选择多余工具；
- 当前 Token usage 未进入公开响应，无法给出可靠单请求成本；
- 严格场景总通过率只有 0.233，不能据此宣称生产可用或安全认证；
- LLM-as-judge 只覆盖少量边界表达，且只能作为辅助指标；
- 当前 30 条场景是固定教学数据集，仍需更丰富设备、环境、拍摄条件和人工标注集验证泛化能力。

## 18. 后续改进方向

后续改进应优先解决系统性问题，而不是继续为单个场景增加关键词规则：

1. 在服务端内部采集 Planner、Vision 和 Judge 的 Token usage，并维护可审计的模型价格版本；
2. 将“视觉观察 → 工程解释 → 当前状态核对”拆成明确任务阶段，减少 Planner 重复检索和来源混淆；
3. 为图片质量、文字可读性、颜色和连接状态建立独立的确定性检查或专用模型；
4. 继续完善 Planner 的停止条件、最小必要工具选择和高风险结束语义；
5. 扩充由人工审核的多设备、多光照、多角度和多噪声评测集；
6. 建立真实但只读的遥测适配器，并保持与模拟 Store 相同的 Provider 或 Protocol 边界；
7. 在进入生产环境前增加身份认证、租户隔离、对象存储、恶意文件检测、速率限制和独立审计日志；
8. 保持视觉观察、知识证据、实时数据和人工确认的来源分层，不允许为了提高通过率而取消安全拒答。

## 19. 最终结论

Week 5 已完成从文本 Agent 到多模态 Agent 的工程扩展：

```text
安全图片输入
+ Vision原生多模态调用
+ OCR与规则基线
+ analyze_robot_image只读工具
+ 请求级图片隔离
+ 视觉、知识、日志和遥测来源分层
+ 30场景批量评测
+ 确定性指标与辅助Judge
+ 脱敏轨迹和成本边界
+ 2214项离线回归
```

本周最重要的成果不是“模型已经能够看图”，而是建立了图片进入 AI 应用时所需的输入安全、来源追踪、权限控制、结构化输出、失败降级和批量评测边界。

当前系统适合作为多模态 AI 应用工程学习项目和受控原型，不适合直接用于机器人控制、现场安全决策或生产故障自动处置。下一阶段如果继续发展，应优先提高任务完成和来源利用的稳定性，并补齐真实成本、身份权限和生产数据接入，而不是仅优化单个评测场景的字面匹配结果。
